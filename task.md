# Build an Immersive, Award-Worthy Full-Stack Developer Portfolio

## 1. Role and objective

Act as a multidisciplinary team consisting of:

- An award-winning creative frontend developer.
- A senior UI/UX and digital experience designer.
- A creative technologist specializing in interactive web experiences.
- A motion designer specializing in spring physics, elastic interactions and fluid transitions.
- A senior Vue 3 developer.
- A senior Golang backend engineer.
- A web performance and accessibility specialist.

Design and develop a complete, production-ready, highly immersive personal portfolio for a backend-focused full-stack developer with 5+ years of professional software development experience.

This must not resemble a generic developer portfolio, template-based landing page, administrative dashboard or AI-generated website.

The portfolio itself must demonstrate engineering expertise, creativity, technical maturity, performance optimization and exceptional attention to detail.

The experience should be memorable enough that recruiters, engineering leaders, developers and potential clients remember it after closing the website.

## 7. Motion design system

Develop a centralized motion system rather than scattering unrelated animation logic throughout components.

Create reusable motion primitives for:

- Spring transitions.
- Elastic dragging.
- Magnetic attraction.
- Inertial movement.
- Rubber-band stretching.
- Velocity-sensitive deformation.
- Staggered reveals.
- Layout transitions.
- Morphing surfaces.
- Scroll-driven sequences.
- Pointer-responsive effects.
- Enter and exit animations.

### Spring physics

Use frame-rate-independent physics where practical.

Model spring movement using position, velocity, stiffness, damping and mass.

Create configurable motion presets for:

- Responsive interface interactions.
- Soft organic movement.
- Heavy physical objects.
- Playful elastic elements.
- Subtle premium transitions.

Animations must feel physically coherent.

Avoid excessive bouncing and long settling times for functional controls.

### Stretchy interactions

Implement selected interactions where surfaces respond to movement and velocity:

- Buttons stretch slightly toward the pointer.
- Project previews deform subtly during dragging.
- Navigation indicators morph between destinations.
- Interactive surfaces compress on press.
- Connected objects stretch and recover.
- Project mockups respond to pointer movement with controlled depth.
- Selected page transitions use elastic masks.

Use deformation selectively. Text must remain readable and controls must remain predictable.

### Scroll behavior

Use native browser scrolling.

Do not hijack scrolling or introduce unnecessary artificial inertia.

Use scroll-driven animation to enhance storytelling, not prevent navigation.

Visitors must be able to quickly reach projects, experience and contact information.

### Reduced motion

Respect prefers-reduced-motion.

Provide an optional motion intensity setting:

- Full experience.
- Reduced motion.
- Minimal motion.

Reduced-motion mode must preserve the content, layout and functionality.

Persist the preference locally.

### Embedded frontend

The build process must:

1. Install frontend dependencies using a lockfile.
2. Run frontend type checks.
3. Run frontend tests.
4. Generate the production Vite build.
5. Copy the generated distribution into the Go embedding directory.
6. Compile the Go application.
7. Produce a standalone executable.

Use Go's embed package to include the production frontend.

Use fs.Sub where appropriate to expose the embedded distribution.

Do not depend on a runtime Node.js installation.

Do not require a separate frontend web server in production.

Do not require the dist directory to exist alongside the executable.

### SPA routing

Correctly serve Vue Router history-mode routes.

Requirements:

- Serve actual embedded assets when requested.
- Return correct MIME types.
- Return 404 for missing static assets.
- Do not return index.html for missing JavaScript or CSS files.
- Return index.html for valid frontend navigation routes.
- Keep API routing separate from SPA fallback.
- Support GET and HEAD requests appropriately.

### HTTP endpoints

Provide:

- GET /healthz
- GET /readyz

Optional endpoints:

- POST /api/contact

Only implement additional endpoints when they provide genuine functionality.

### HTTP configuration

Include:

- Configurable listen address and port.
- Read header timeout.
- Read timeout.
- Write timeout.
- Idle timeout.
- Maximum request body limits.
- Graceful shutdown.
- Structured request logging.
- Panic recovery.
- Appropriate security headers.
- Request IDs.

### Static asset optimization

Implement:

- Long-lived immutable caching for hashed Vite assets.
- Appropriate revalidation for index.html.
- Correct content types.
- ETag or equivalent validation where practical.
- Optional build-time Brotli and gzip compression.
- Correct Accept-Encoding negotiation.
- Vary headers for compressed assets.

Avoid compressing already compressed media formats unnecessarily.

### Contact form

- Validate and sanitize inputs.
- Limit request sizes.
- Implement reasonable rate limiting.
- Include spam protection.

## 17. Performance requirements

The portfolio must demonstrate that visually sophisticated applications can still be efficient.

Treat performance as a product feature.

### Rendering optimization

- Prefer transform and opacity animations.
- Avoid repeated layout calculations.
- Avoid excessive DOM nodes.
- Avoid permanent will-change declarations.
- Use one coordinated animation loop where practical.
- Pause offscreen animations.
- Pause unnecessary rendering when the browser tab is hidden.
- Use adaptive rendering quality.
- Cap device pixel ratio where appropriate.
- Avoid unnecessary GPU post-processing.
- Lazy-load heavy visual modules.
- Dispose of rendering resources correctly.
- Avoid large uncompressed textures.
- Provide non-WebGL fallbacks.

### Performance budgets

Target the following under documented representative test conditions:

- LCP of 2.5 seconds or less.
- CLS of 0.1 or less.
- INP of 200 milliseconds or less.
- Lighthouse accessibility score of at least 95.
- Lighthouse performance score of at least 90 where practical.
- Approximately 60 FPS on capable devices.
- Stable, usable rendering on mid-range mobile devices.
- Minimal initial JavaScript.
- Initial compressed JavaScript target below 200 KB where practical, excluding deferred creative rendering modules.

Treat these as measurable targets rather than guaranteed results.

Document actual results and trade-offs.

### Adaptive quality

Implement quality tiers:

- High-quality creative rendering.
- Balanced rendering.
- Lightweight rendering.
- Static accessible fallback.

Select initial quality using conservative capability checks.

Adapt quality when sustained frame timing indicates performance problems.

Do not continuously run expensive device benchmarks.
